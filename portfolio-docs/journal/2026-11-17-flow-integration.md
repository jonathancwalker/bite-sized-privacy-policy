# Flow integration checkpoint

The user corrected the proposed next priority: benchmarking can wait; the immediate goal is a good user experience and working flow. This supersedes the assistant's proposed gold-set-first order, while preserving semantic evaluation as a later need. Source: current project conversation, November 17, 2026.

Before changes, the private static prototype accepted paste, TXT, and a fictional sample. The separate intake/LLM tooling accepted catalog, URL, paste, and TXT/RTF/DOCX/PDF, but was not connected to the browser. The browser showed exact source passages with keyword topics and generic titles, not model claims. A read-only agent reviewed the existing 390 × 844 mobile view: the policy input began below the first viewport, the overview's continue action was about 1247 px down, and review reactions began around 805 px. It also found that one card could combine several propositions under one reaction, while empty report sections could obscure actual questions and concerns. These are QA observations, not user-study results.

Implementation direction for this pass: make the four intake choices visible, preview extracted text, build one reaction per claim with exact source access, make primary actions appear earlier on mobile, and place substantive report content before empty categories. A local same-origin API can reuse the existing Node intake and LLM modules without exposing the key in browser code. The hosted Site is static; server-backed deployment needs separate migration and secret configuration.

The user then clarified that a simple or fake front end is sufficient for now; testing the plumbing is the priority. Codex connected a local same-origin API to the existing browser flow. The server now handles catalog, URL, paste, and TXT/RTF/DOCX/PDF intake and calls the model with a server-only key. The browser shows an extraction preview, converts accepted model proposals into individually reactable cards, keeps exact source and cited context, and offers exact-passage fallback if generation fails. It retains reactions and report export locally. An independent agent reviewed the code and caught an async navigation race; leaving an import or analysis now invalidates its pending response. It also identified visibility gaps for partial model output, blocked catalog pages, and long extraction previews, which were addressed with notices, official source links/paste path, and a scrollable full-text preview.

In a local browser run, the fictional sample produced 19 source-linked draft claims. One saved clarification survived refresh and appeared in the partial report; a downloaded report contained the question, all claims, exact cited quotes, and the complete policy. A TXT upload showed the expected extracted text. The Anthropic catalog and arbitrary URL paths each returned 40,685 characters through the local API. At 390 × 844, the new claim card showed reactions within the first viewport and report access was restored on mobile. These are implementation checks using synthetic inputs, not comprehension or semantic accuracy evidence. See [E04](../experiments.md#e04--connected-local-review-flow).
